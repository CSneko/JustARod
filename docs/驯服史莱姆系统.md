# 驯服史莱姆系统（Tamed Slime）

> 本文档记录本功能的完整设计规格、实现位置与实测指引，对应版本 JustARod 1.3.0（Minecraft 26.1.2 / Architectury）。

## 1. 玩法总览

| 功能 | 行为 |
| --- | --- |
| 驯服 | 对**体积最小（size=1）**的野生史莱姆喂粘液球累计信任（10 个），信任满后用**史莱姆铃铛**右键确认，野生史莱姆转化为驯服史莱姆并绑定主人 |
| 跟随 / 待命 | 默认跟随主人（超过 8 格开始跟随、2.5 格停下、超过 12 格直接传送）；GUI 里可切换「跟随 / 待命 / 吞人」 |
| 战斗 | **只打主人正在打的目标**（不主动索敌）；主人挨打时只是记仇不主动出击 |
| 物品收纳 | 1 组物品 = 1 格空间；容量随等级指数增长（4 → 11 → 32 → 90 → 256 → 724 组） |
| 实体收纳 | 边长 > 2 格（level ≥ 3）才能吞实体；实体按碰撞箱体积（长×宽×高，半格向上取整）占用同一空间池；**自动模式**不吞玩家、不吞队友宠物 |
| 主人进出 | 空手右键自己的史莱姆 = 钻进去；体内按移动键操控它走动、空格跳跃；**潜行键钻出（只对主人有效）**；体内按 **B** 打开它的背包。主人在体内时**会登记为体内内容**（实体页看得见、占格），但**免疫挣扎**（不会被自动漂移甩出去，那是他的操控位） |
| 被吞者 | 无法移动、无法攻击、视线被锁在体内；随时间自动漂移逃出，也可连点 **R** 挣扎加速 |
| 分解 | 喂**分解催化物**开启「逐个分解」队列：物品 1 秒/组、实体 5 秒 + 最大生命×0.5 秒；先回血、满血后转成长进度、进度满升级（可连升），level 5 后转 XP。**主人也可以被分解**（包括他自己正在操控史莱姆时；按正常死亡结算：掉落 + 重生） |
| 手动吞噬 | 骑着史莱姆按 **G**：前方 120° / 3 格内最多吞 `min{剩余空间, 等级}` 个生物；先把外观放大到 4 倍、吞完再缩回；黏糊吞咽音效；冷却 30 秒（每头史莱姆各自记账） |
| 死亡 | 驯服史莱姆会死；死亡时体内物品全部掉出、实体全部释放；铃铛可原地召回（30 秒冷却） |

## 2. 体积刻度（SlimeTier）

刻度采用「连续整数指数」：碰撞箱边长 = 2^(level/2) 格，容量 = 4×2^(1.5×level) 组。

| level | 边长（格） | 内部空间（格） | 容量（组） | 最大生命 | 升级所需内容量 |
| --- | --- | --- | --- | --- | --- |
| 0 | 1.0 | 1 | 4 | 20 | — |
| 1 | 1.45 | 3 | 11 | 30 | 11 |
| 2 | 2.0 | 8 | 32 | 40 | 32 |
| 3 | 2.85 | 27 | 90 | 50 | 90 |
| 4 | 4.0 | 64 | 256 | 60 | 256 |
| 5 | 5.5 | 166 | 724 | 70 | 724 |

- 属性：最大生命 = 20 + level×10（用属性修饰符实现，跨加载器安全）
- 升到 level L 的成本 = level L 的容量，因此「越大越慢」
- 收纳实体的门槛是 level ≥ 3（边长 2.85 > 2 格）

## 3. 右键交互优先级

| 手持 | 潜行 | 效果 |
| --- | --- | --- |
| 史莱姆铃铛 | — | 主人：召回（跨维度，30 秒冷却）；他人：提示归属 |
| 任意 | 是 | 打开体内容器 GUI |
| 可堆叠物品 | 否 | 投入一整组（1 组 = 1 格；空间不足时提示，不消耗物品） |
| 空手 | 否 | 主人：钻进体内；他人：打开 GUI |
| 分解催化物（对实体使用） | — | 主人：开启一批分解（最多 max(容量/4,1) 组，每组 4 秒），消耗一份催化物；批内拒绝再喂 |

> ⚠️ 上表只适用于玩家**站在史莱姆外面**的时候。钻进体内后玩家是乘客，
> 右键全部被「操控载具」吃掉、`mobInteract` 不会被调用，所以体内那两件事另有入口：
> **开背包 = 按键 B**（见 §10.1）、**钻出 = 直接按潜行键**（见 §10.8 第 (6) 条）。
> 也就是说潜行键在两个状态下含义不同：站在外面时是「开背包」的修饰键，
> 在体内时是「逃出」。

野生史莱姆：手持粘液球右键喂食（size 必须为 1，否则提示「太大」）。

## 4. 界面与按键

- **容器 GUI**：箱子式界面 + 「物品 / 实体」页签
  - 物品页：9×6 格/页，**一格 = 一整组**（上限取物品自身堆叠上限），底部 `◀ ▶` 翻页（level 5 共 14 页）
  - 实体页：列表显示刷怪蛋图标 + 名字 + 占格 + 挣扎进度条，点右侧 `×` 放出实体
  - 底栏中间按钮：循环切换「跟随 / 待命 / 吞人」
  - 容量显示：`容量: 已用 / 总数`
- **按键**：
  - `key.justarod.slime_struggle`（默认 **R**）——被吞入体内时连点挣扎
  - `key.justarod.slime_bag`（默认 **B**）——**在体内**打开史莱姆背包
  - `key.justarod.slime_devour`（默认 **G**）——骑着史莱姆时手动「吞噬」
- **屏幕右侧提示**（骑着史莱姆时）：`史莱姆 Lv.N` / `按 G 吞噬`（冷却中显示 `冷却 Ns`，
  无目标变灰）/ `按 B 打开背包`。挂在 `VanillaHudElements.SUBTITLES` 之后，
  所以菜单 / F3 调试屏打开时自动隐藏。

## 8. 需要实测确认的点（作者跑游戏时重点看）

1. **外观是否符合预期**：模型结构已经与原版 `SlimeModel` 逐位对齐（见 9.2），
   外壳边长 = 碰撞箱边长 = blockSize 格。**建议按 F3+B 开碰撞箱显示确认**：
   立方体应当正好包住碰撞箱。若仍明显偏大/偏小，改渲染器里那一行 `scale` 即可。
   体内内容靠外壳半透明透出（原版贴图 alpha=180），若看不见则是半透明排序问题。
2. **实体缩放**：体内实体缩到 0.35 是否合适（玩家模型可能仍显大或穿壳）。
3. **操控手感**：`getRiddenSpeed = 0.32` 与跳跃是否跟手；史莱姆的跳跃式移动（MoveControl）
   在玩家操控下是否还有残留的自发跳跃。
4. **GUI 布局**：物品页/实体页切换、翻页、`×` 取出实体的点击热区是否对得上。
5. **体内视角**：被吞时视线被锁在体内是否好受（当前每 tick 强制对齐史莱姆朝向）。
6. **混合端（NeoForge + Forgified Fabric API）**：`ModelLayerRegistry`/`EntityRendererRegistry`
   来自 Fabric API，需要确认在 NeoForge 侧也能正常注册渲染。
7. **贴图**：史莱姆**不需要**自带贴图（复用原版）；两个新物品的贴图是程序生成的占位图，
   建议替换成正式美术。
8. **本轮新增（第十二轮，§10）**：
   - **按键能不能用**：钻进体内按 **B** 应能打开背包（别人按 B 无反应，服务端拒绝）；
     骑着史莱姆按 **G** 应有反应。若「按了连提示都没有」，先看设置里的
     「按键绑定 → 只是根棍子」里 B / G 是否真的绑上了，再回来看
     §10.7（客户端拿 `ownerUuid` 做门禁就会是这种「静默失效」的症状）。
   - **主人可被分解**：启动分解后主人被正常分解（掉落 + 经验 + 重生）；
     同时确认**主人站在旁边不会被自动吞**（自动模式仍不吞玩家）。
   - **吞噬技能手感**：4 倍放大是否够震撼、0.45 秒的「张开→吞→收回」节奏是否跟手；
     放大期间碰撞箱不变，因此**外形会比碰撞箱大一圈**（需求确认只要视觉），
     看是否可接受；`DEVOUR_ANIM_TICKS`（18）与 `DEVOUR_SCALE`（4.0）都可直接调。
   - **吞咽音效**：`assets/justarod/sounds/slime_swallow.ogg` 是否够「黏糊」；
     不满意就用 `.tmp/slime_sound/alt/` 里的变体覆盖，或改
     `.tmp/slime_sound/gen_swallow.py` 的 `VARIANTS` 重新生成。
   - **右侧提示**：改键后提示里的按键名是否跟着变（按键名走
     `KeyMapping#getTranslatedKeyMessage()`）；冷却倒计时与技能实际可用时机是否对得上；
     F3 / 暂停菜单打开时提示是否正常隐藏。


## 9. 踩坑记录（26.1.2 迁移经验）

### 9.1 不要在 common 侧用 `@Accessor` 访问原版私有字段

第一版为了「翻页时重建槽位」，用 `@Accessor("slots")` + `@Invoker("addSlot")` 打开
`AbstractContainerMenu`。构建时报了：

```
Cannot remap slots because it does not exist in any of the targets [AbstractContainerMenu]
```

我把它当成噪音忽略了，结果**客户端启动直接崩**：

```
InvalidAccessorException: No candidates were found matching slots:Ljava/util/List;
```

原因：本工程是 official（Mojang）命名空间 + 无 refmap，mixin 的成员名直接进产物；
但 `slots` 是 `AbstractContainerMenu` 里的字段，Loom 在重映射阶段找不到对应成员、
没能把它写进产物，于是运行时按字面名找不到字段。

**现在的做法**：槽位对象**永不重建**。菜单固定建 54 个槽位，
`SlimeStorageContainer` 作为「分页窗口」（`pageOffset + 槽位下标` → 真实物品格），
翻页只移动窗口偏移。既不需要碰 `slots`，也不需要任何 accessor。

> 判断规则：`@Accessor`/`@Invoker`/`@Inject` 指向**原版已有的成员**时，
> `Cannot remap ...` 警告是**真错误**，必须处理；
> 指向**自己 mixin 注入的成员**（如 `SlimeTrustAccessor` 的 `justarod$trust`）时，
> 这个警告是**预期噪音**，可以忽略。


### 9.2 贴图密度：模型像素 = 贴图像素（这次外观翻车的真凶）

第一版外壳用了 16 像素立方体 + `texOffs(0,0)`，结果游戏里史莱姆变成一个大方块、
脸上是 2×2 的方块网格。原因是 **box-UV 下 `texOffs(0,0)` 的 UV 跨度 = 立方体边长**：
边长 16 时每个面要跨 16 个贴图像素，而原版贴图的脸部只有 8x8，
于是眼睛/嘴被放大成 2×2 大方块。

`./gradlew :fabric:dumpSlimeModel`（临时任务，已删）把烘焙后的顶点/UV 打出来对比，
实测结论：

| | 原版外层 | 原版内层 | 我的模型 |
| --- | --- | --- | --- |
| 立方体数 | 1 | 4（内核+两眼+嘴） | 5（同左） |
| 外壳尺寸 | `-4..4 / 16..24` | — | `-4..4 / 16..24` ✅ |
| 眼睛 | — | `±3.25, 18..20, -3.5..-1.5` | 同 ✅ |
| 嘴 | — | `-1..0, 21..22` | 同 ✅ |
| 内核 | — | `±3, 17..23` | 同 ✅ |

另外两点（从原版 `SlimeRenderer` / `SlimeOuterLayer` 字节码确认）：

- 原版渲染器的主模型是**内层**（`ModelLayers.SLIME`），半透明外壳由 `SlimeOuterLayer`
  单独画（缩放 `size * 1.02`）。本模组用单体模型把两者合并，结构等价但更简单；
  代价是**不能做外壳挤压动画**（缩放外壳会让贴在壳上的眼睛/嘴陷进去或凸出来），
  所以 `setupAnim` 刻意留空。
- 脸部三块的贴图坐标：**右眼 `(32,0)`、左眼 `(32,4)`、嘴 `(32,8)`**。
  写成 `(0,16)` 会落在**透明**调色板区域（那张 64x32 贴图有 12 色索引，
  索引 0 的 alpha 是 0），结果是脸上什么都没有——第一版就是这个坑。

三条硬结论（26.1.2 实体模型）：

1. **16 像素 = 1 格**，且模型空间 **Y=16 是地面**（原版 0.5 格高的 size-1 史莱姆，
   外壳 cube 正是 `y=16..24`）；
2. **1 模型像素 = 1 贴图像素**：要让外观方块边长等于 N 格，就用 `8*N` 像素的立方体，
   再由渲染器按比例缩放（缩放不改变 UV 密度）；
3. 眼睛/嘴/内核是**单独的立方体**（原版放在内层模型里），
   不能指望靠外壳贴图整体拉伸做出脸。


### 9.3 客户端菜单槽位数必须与服务端一致

第二版崩在容器内容包上：

```
IndexOutOfBoundsException: Index 87 out of bounds for length 46
  at AbstractContainerMenu.setRemoteSlot
  at ClientPacketListener.handleContainerSetSlot
```

原因：26.x 的 `MenuType` 工厂只有 `(containerId, Inventory)` 两个参数，
**客户端构造菜单时拿不到实体**，所以第一版客户端只建了玩家背包那部分槽位（数量对不上），
而服务端按等级建了完整槽位。服务端一广播内容，客户端就往不存在的下标写 → 直接掉线。

修法：服务端在 `openMenu` 之后**立刻**补发一个 `SlimeMenuContextPayload`（等级 + 实体 id）。
两个包同连接有序，而容器内容包要等服务端下一 tick 的 `broadcastChanges` 才发出，
所以客户端一定先拿到等级、在构造菜单时就建出与服务端**逐一对齐**的槽位。

配套改动：

- `SlimeStorageContainer.capacity()` 改成**纯计算**（服务端用实体等级、客户端用同步等级），
  不再依赖「实体是否在客户端存在」——这正是崩溃的根源；
- 容器内的每个格子改成**一整组物品**（栈上限 64），不再是「一格一个物品」，
  否则把一组 64 个往「上限 1」的槽位里放会被原版逻辑拒收；
- 升级会改变容量（= 槽位数），而 `slots` 是 final 的、26.x 无法增删，
  所以实体每 tick 检查「已打开界面且容量已变」时主动关掉界面并提示重开
  （`closeOutdatedMenus` / `slotCountOutOfSync`）。

### 9.4 `MenuScreens.register`

不注册界面工厂时原版会打印
`Failed to create screen for menu type: justarod:slime_menu`，并留一个打不开的空界面。
`MenuScreens.register` 是私有的，因此在 access widener 里加了一行；
注册后 `SlimeScreen` 由原版正常创建，客户端 tick 里那次替换只作为兜底。


### 9.5 `Item#interactLivingEntity` 在 26.x 基本不生效

第二版里「史莱姆铃铛」和「分解催化物」的右键逻辑写在
`Item#interactLivingEntity` 里，结果铃铛完全没反应、催化物被当成普通物品塞进体内。
原因是 26.x 的右键实体分发已经改成：

```
Player#interactOn → Entity#interact(player, hand, hitVec) → Mob#interact
   └─ Mob#checkAndHandleImportantInteractions  ← 只有「命名牌 / 刷怪蛋」才会调用
      ItemStack#interactLivingEntity
```

也就是说**自定义物品的 `interactLivingEntity` 永远不会被调用**。修法：

- 已驯服史莱姆（铃铛召回 / 催化物分解）：逻辑搬进 `TamedSlimeEntity#mobInteract`
- 野生史莱姆（喂粘液球攒信任 / 铃铛确认驯服）：新增 `SlimeInteractMixin`
  注入 `Slime#mobInteract` 的 HEAD，用 `Cir.setReturnValue` 接管
- 两个物品类退化成「纯物品 + 工具方法」，不再依赖 `interactLivingEntity`

### 9.6 客户端容量被覆盖的 bug

`SlimeMenu` 构造末尾的 `applyPageOffset()` 原本写成
`container.setClientTierLevel(slime == null ? syncTier.get() : slime.getTierLevel())`。
客户端构造时同步槽还没收到值，`syncTier.get()` 返回 0，于是把刚由「上下文包」设好的等级
又冲成 0 → **容量恒为 4、翻页永远只有 1 页、超出容量的格子判断也全错**。
现在只有服务端（`slime != null`）才写这个值。

> 排查手段：`SlimeMenu` 的容量/槽位逻辑可以脱离游戏验证——
> 临时写一个 `JavaExec` 任务，`SharedConstants.tryDetectVersion() + Bootstrap.bootStrap()`
> 之后直接 `new SlimeMenu(...)` 并打印 `slots.size() / capacity() / isReal(n)`，
> 比进游戏点一遍快得多（本工程的 `:fabric:` 有 `runtimeClasspath`，很便宜）。


### 9.7 `@Inject` 的目标方法必须由目标类**自己声明**（Mixin 默认不搜父类）

第三版启动直接崩：

```
InvalidInjectionException: Critical injection failure:
@Inject annotation on justarod$tameInteraction could not find any targets
matching 'mobInteract' in net/minecraft/world/entity/monster/Slime
```

实测（`javap` 核对）：`interact` 和 `mobInteract` **都是 `Mob` 声明的，`Slime` 一个都没覆写**，
而 Mixin 的默认目标选择器只在该类自身声明的成员里找 → 注入必然失败。

**规则**：注入前先 `javap` 确认目标方法声明在哪个类，然后 `@Mixin` 那个类（而不是子类），
再用 `instanceof` 做类型守卫。现在 `SlimeInteractMixin` 注入的是 `Mob#interact`。

### 9.8 离线校验 `@Inject` 目标：`:common:verifyMixins`

这类失败编译期完全看不出来（编译能过、打包能过，一进游戏就崩），所以加了校验任务：

```bash
./gradlew :common:verifyMixins
```

它用 ASM 读取编译产物与 `justarod.mixins.json`，对**已注册**的 mixin 逐个检查
`@Inject.method` 在目标类自身声明的成员里是否存在。两个实现细节：

- `@Mixin` 是 `RetentionPolicy.CLASS` → 注解在 ASM 里位于 **`invisibleAnnotations`**
  （只读 `visibleAnnotations` 会扫到 0 个，静默假通过）；
- `@Inject#method` 的值是**数组**，要取第一个元素，直接 `toString()` 会得到 `[interact]`。

结果分类：`OK` / `MISSING`（真问题，退出码 1）/ `UNRESOLVED`（第三方模组类，只提示不报错）。
当前状态：40 个已注册目标全部 `OK`；`EnderDragonRendererMixin` 注入的 `render` 在 26.x
已改名为 `submit`（所以那句 `Cannot remap render` 是真问题），但该 mixin **并未在配置里注册**，
是死代码，算是已知遗留。


### 9.9 永远不要在 tick 里「替换」已打开的容器界面

第四版的症状：**服务端体内确实有物品（按空格能把物品快捷移动出来），但 GUI 里永远是空的**，
客户端的槽位日志一律 `0:-`，而且 `SlimeMenu.initializeContents` 在客户端**一次都没被调用**。

根因是界面创建方式。原来为了用上自定义界面，走的是「让原版按 `MenuType` 造一个通用箱子界面，
然后在 `ClientTickEvents.END_CLIENT_TICK` 里 `setScreen(new SlimeScreen(...))` 换掉它」。
而 `Minecraft#setScreen` 会对旧界面调用 `removed()`，`AbstractContainerScreen#removed()`
又会调用菜单的 `onClose()` → **客户端把还在同步中的菜单关掉了**，
于是服务端的容器内容包全部落空，界面自然永远是空的。

修法：**不要在 tick 里替换**，而是让原版的界面工厂直接造出我们的界面：

```java
MenuScreens.register(JRMenus.SLIME_MENU, SlimeScreen::create);
```

`MenuScreens.register` 是私有的，已在 access widener 里加了一行；
工厂拿不到实体，所以服务端在 `openMenu` **之前**先发 `SlimeMenuContextPayload`
（实体 id + 等级），客户端收到后放进静态待用上下文，工厂里取出来用。

> 排查这类问题的一个有效信号：**两端日志对照**。
> 服务端 `player.containerMenu` 里还有物品（快捷移动能用），
> 客户端却收不到 `initializeContents` —— 那多半不是同步包的问题，而是界面/菜单生命周期
> 把菜单提前关掉了。


### 9.10 客户端容器必须有自己的存储，否则同步包等于「写进空气」

第五版症状（诊断日志）：

```
[Render thread/INFO]: [包] handleContainerContent containerId=1 stateId=1 items=90 当前菜单=SlimeMenu
[Render thread/INFO]: [菜单] initializeContents 菜单=SlimeMenu stateId=1 items=90
[Render thread/INFO]: [菜单] 写入后 slots=90 读到=[0:- 1:- 2:- 3:- ] 传入=[0:1xminecraft:slime_ball 1:1x… 2:1x… 3:1x… ]
[Render thread/INFO]: [SlimeMenu诊断] 界面渲染中 侧=客户端 … cap=4 … items=[0:-/a 1:-/a 2:-/a 3:-/a 4:-/x 5:-/x ]
```

注意这三件事同时成立：内容包**到了**、`initializeContents` **被调用了**、传入的物品**有值**，
但「写入后」立刻读回来全是空；与此同时鼠标点击仍然能放入/取出物品。

根因在 `SlimeStorageContainer`：客户端侧 `slime == null`（`MenuType` 工厂拿不到实体），
而当时**每个方法**都以 `if (slime == null) return …` 开头，读写全部转发到实体存储：

```java
public ItemStack getItem(int slot) {
    if (index < 0 || slime == null) return ItemStack.EMPTY;   // 客户端恒返回空
}
public void setItem(int slot, ItemStack stack) {
    if (index < 0 || slime == null) return;                   // 客户端直接丢弃
}
```

而 `AbstractContainerMenu#initializeContents` 写入内容的**唯一**途径就是
`getSlot(i).set(stack) → Slot#set → Container#setItem`
（26.1.2 的字节码核对过；单槽位包 `ClientboundContainerSetSlotPacket` 也一样，
只是走 `AbstractContainerMenu#setItem(int,int,ItemStack)`，**不是** `setRemoteSlot`）。
客户端没有实体 → `setItem` 直接 return → 同步包写进空气。

点击为什么「看起来正常」：点击只发 `ServerboundContainerClickPacket`，服务端在**真实容器**上
搬运物品并把结果回包；客户端那侧因为槽位恒空，预测（`doClick`）什么也没做，
所以「功能正常、显示全空」。

修法：客户端这一侧保留一份**本地镜像** `SlimeStorageContainer#clientItems`。
`slime != null` 读写实体存储（唯一真相，菜单关掉后物品仍在体内），
`slime == null` 读写镜像；`getItem / setItem / removeItem / removeItemNoUpdate /
isEmpty / clearContent` 统一走 `backing()`。镜像只增不减，等级同步晚到不会抹掉已收到的物品。

顺带修掉两处同类毛病：

1. **`tierLevel` 只写不读**：`setTierLevel` 里有 `entityData.set(DATA_TIER, …)`，
   但没有任何地方读回来，客户端实体的 `tierLevel` 恒为 0。
   于是 `SlimeScreen.create → menu.setClientSlime(entity)` 又把「上下文包」刚设好的等级
   冲成 T0 —— 容量 4、`getMaxPage()` 恒 0，90 个槽位只有前 4 格可见可点（§9.6 的翻版，
   只是这次是从实体那边冲进来的）。现在 `TamedSlimeEntity#onSyncedDataUpdated` 回填 `DATA_TIER`，
   并且 `setClientSlime` 只在「上下文包没给等级」时兜底（`hasClientTierLevel()`）。
   实体尺寸不用自己管：原版 `Slime` 的 `ID_SIZE` 已经同步，`getSize()` 就是读它。
2. **诊断计数是假的**：`clientInitCalls` 声明之后从未自增，日志里的「收到内容次数=0」
   纯属误导；单槽位更新挂在 `setItem` 入口才不会漏（`setRemoteSlot` 只用于「玩家背包菜单」）。

验收信号（同一套日志）：

- `[菜单] 写入后 … 读到=[0:1xminecraft:slime_ball …]` —— 读回来不再是空；
- `[SlimeMenu诊断] 侧=客户端 … 收到内容次数≥1 … items=[0:1x…/a …]`；
- 高等级史莱姆：`tier` / `cap` 与服务端一致、翻页按钮可用、渲染尺寸也跟着对。

已知遗留（见 §9.11、§9.12 的后续处理）：

- `SlimeContentsLayer` 里**物品**那一半仍然画不出东西：物品列表从来没有同步给客户端，
  客户端 `storage().items()` 恒为空。要修得单开一个同步包，把「体内物品摘要」推给追踪该实体的玩家。
  （**实体**那一半已修：改成遍历客户端真实乘客，见 §9.12。）
- ~~容量语义自相矛盾~~：已在 §9.11 统一为「1 格 = 1 组」。


### 9.11 「1 格 = 1 组」的语义统一 + 存档被空槽卡死

两件事一起说，因为它们是同一处代码的两面。

**（1）存储单位从「个」改成「组」。** 之前三处写法不一致：

| 位置 | 旧行为 |
| --- | --- |
| 文档 §9.3 | 1 格 = 1 组（上限 64） |
| `SlimeStorageContainer#getMaxStackSize()` | 返回 64 |
| `SlimeMenu#addSlots` 的 `Slot#getMaxStackSize()` | 覆写返回 **1**（实际生效的是这个） |
| `SlimeStorage#addItem` | `copyWithCount(1)`，一次只放 1 个 |

结果就是「一格一个物品」——喂一组 64 个进去只剩 1 个，GUI 里也堆不起来。
现在统一成「1 格 = 1 组」：

- 删掉 `Slot#getMaxStackSize()` 覆写，改用 `container.getMaxStackSize()`（64）
  与物品自身上限的较小值（原版 `Slot#getMaxStackSize(ItemStack)` 的语义）；
- `addItem` 整组塞进第一个空格，返回**实际投入的物品数**，调用方按这个数 `stack.shrink(...)`；
- 空间账本不变：一个非空格 = 1 格（`usedSpace()`），和容量、成长进度、分解批次同一套单位。

**（2）存档报错 `Failed to append value '0 minecraft:air' to list 'Items'`。**
`SlimeStorage#save` 为了保住「下标 = 槽位」的对应关系，会把空槽也写进列表，
但用的是严格的 `ItemStack.CODEC`——它校验「数量 ∈ [1;99] 且不能是 `minecraft:air`」，
于是写第一个空槽就抛错（顺带整只史莱姆的存档一起丢）。

修法：换成 `ItemStack.OPTIONAL_CODEC`（读也用同一个）。它把空栈写成 `{}`，读回来还是空栈：

```
Items:[{count:64,id:"minecraft:slime_ball"},{count:7,id:"minecraft:dirt"},{},{}]
```

下标完全不丢，也不再抛错。离线验证见 §9.12 末尾的测试。

### 9.12 催化分解：一批一组 4 秒，物品一个个被吃掉

旧逻辑：一份催化物 = 一个分解任务 = 分解一份内容（1 个物品 1 秒、1 个实体 5 秒 + 最大生命×0.5 秒）。

新规则（与作者确认）：一份催化物开启**一批**分解，最多处理 `max(容量/4, 1)` 组物品或实体
（T0=1、T3=22、T5=181），**每组固定 80 tick（4 秒）**，批内连续进行；
**一批没跑完之前再喂催化物会被拒绝，且不消耗物品**（先判定再扣物品）。

- `decomposeBatchSize()` / `isDecomposing()` / `addDecomposeTask()`（返回 false = 已有批次）；
- `ITEM_DECOMPOSE_TICKS` / `ENTITY_BASE_TICKS` / `ENTITY_SECOND_PER_HEALTH`
  三个常量合并成 `DECOMPOSE_STEP_TICKS = 80`；
- 右键喂与 GUI 的 `ACTION_FEED_CATALYST` 共用 `useCatalyst(...)`，规则完全一致；
- `DecomposeTasks`（剩余组数）本来就在存档里，所以区块卸载/重进世界后批次会接着跑；
- 实体步骤的血量代价与「血量不足挂起」保留：挂起时批次仍在跑，因此同样拒绝新催化物；
  想解锁可以往体内塞物品（分解物品会回血）。

**（1）「总时长 4 秒」与「一个一个消耗」是可以同时成立的。**
一组 = 一格（最多 64 个物品）。组内不再「整叠瞬间消失」，而是按时间均匀地一个个吃掉：
第 k 个物品在本组走到 `k/count` 时被吃掉（`consumedItemsAt`），
所以一叠 64 个 ≈ 每 tick 掉一个、最后一个正好落在组末；一格只有 3 个时分别是
第 27 / 54 / 80 tick 掉一个。每个物品回 1 点血，溢出部分攒够 1 点转成成长进度。
GUI 开着时 `broadcastChanges()` 会把这些变化逐 tick 推给客户端，能直接看到格子一点点空下去。

**（2）`decomposeTimer` 从来没被种上（"速度像 4 tick" 的真凶）。**
`beginDecomposeStep()` 只设了 `decomposeTotal`，没有 `decomposeTimer = decomposeTotal`，
于是每步都是「开始后下一 tick 立刻结束」——一组 ≈ 1 tick，一整批 22 组一秒内跑完。
现在物品组和实体组都在开始处计时。

**（3）成长按「组」结算。** 分解掉的物品数量先攒在 `pendingGrowthItems` 里，
每 80 tick（4 秒）结算一次：满 64 个 = 1 格成长进度（`addGrowthProgress`），
余数留到下一个周期——所以两格各 30 个（= 60）不会给进度，攒到 64 才给 1 格。
实体仍按体积（碰撞箱格数）在组末直接计进度。

### 9.13 体内实体渲染：外壳只有设计值的一半（截图里"站在史莱姆头上"的根因）

前面两版分别试过「图层画缩小副本」「隐藏原版乘客渲染」，都不对——因为**位置本身**就是错的。

模型空间的三条硬约定（26.x，`javap` + 作者自己的 `dumpSlimeModel` 结论）：

1. **16 像素 = 1 格**；
2. 外壳用的是原版那张贴图要求的 **8 像素立方体**（每面 8×8 贴图像素，见 §9.2），
   也就是**只有 0.5 格**；
3. 模型 **+Y 朝下**，外壳位于 `y = 16..24 像素`（= 1.0..1.5 格），原点在地面上方约 1.5 格。

于是 `JRTamedSlimeRenderer#scale` 里只乘 `blockSize` 是错的：
外观边长只有 `0.5 × blockSize`（T3 = 1.43 格，而不是设计表的 2.85 格），
而 `getPassengerAttachmentPoint` 按 `blockSize` 算（`0.45 × blockSize = 1.28` 格）——
**挂载点直接落到壳顶之上**，玩家看起来就像"站在史莱姆头上"（截图那一幕）。

修法三件（互相配套）：

- `scale(blockSize * 2)`：让外观边长真的等于 `blockSize` 格（与 §5 数值表的「实际边长」一致，
  粒子中心 `blockSize * 0.5`、挂载点等按 `blockSize` 算的地方也才对得上）；
- `getPassengerAttachmentPoint`：按**乘客自身高度**竖直居中（再下压 5% 给耳朵/帽子留余量），
  水平半径按乘客宽度夹在壳内 → 整个实体真正待在体内；
- 删掉 `SlimePassengerRenderMixin` 与图层里的实体绘制：乘客由原版渲染器直接画在体内，
  透过半透明外壳就能看到（这正是模型 javadoc 里写的设计意图），也不会出现里外两个分身。

`SlimeContentsLayer` 现在只负责**物品**，并且偏移改成了真实的空腔中心
`(0, 1.25, 0)`（模型空间）——早期版本按 `(0, 0.5, 0)` 写，会被 Y 翻转与 -1.501 的平移
带到壳顶上方去。

**（3）离线验证。** 26.1.2 起物品组件由数据包初始化器绑定，裸 JVM 里 `new ItemStack(...)`
会抛 `Components not bound yet`，测试里手动 `((Holder.Reference<Item>) BuiltInRegistries.ITEM
.wrapAsHolder(Items.SLIME_BALL)).bindComponents(DataComponentMap.EMPTY)` 即可绕过。
配合 `SharedConstants.tryDetectVersion() + Bootstrap.bootStrap()`，
`.tmp/jrtest/` 下的两个用例（客户端镜像写回、组语义 + 存档往返）都能脱离游戏运行：

```
Items:[{count:64,...},{count:7,...},{},{}]   # 空槽不再抛错，读回下标不丢
```


### 9.14 史莱姆的移动、操控与外观（第五轮修正）

**（1）跟随失效的真凶：`SlimeMoveControl` 不认坐标。**
26.x 的 `Slime.SlimeMoveControl` 比基类 `MoveControl` 更"笨"：

```java
// 它自己的 tick()（反编译结论）
setYRot(rotlerp(getYRot(), this.yRot, 90F));       // 只朝内部字段 yRot 转
if (operation != MOVE_TO) { setZza(0); return; }   // 没在移动就站住
operation = WAIT;
if (onGround()) { setSpeed(speedModifier * MOVEMENT_SPEED); /* jumpDelay… */ getJumpControl().jump(); }
```

也就是说它**只认两样东西**：内部朝向 `yRot`（只能由 `setDirection(yaw, aggressive)` 改）
和 `speedModifier`（只能由 `setWantedMovement(speed)` 改）。
旧代码调的是基类 `MoveControl#setWantedPosition(x, y, z, speed)`——那只写 `wantedX/Y/Z`
并把 operation 置成 MOVE_TO，而 `SlimeMoveControl` 从不读这三个字段，
于是史莱姆永远朝"出生时记录的朝向"跳：**不会跟人走，只会在 12 格外直接传送过来**。

修法（原版 `SlimeAttackGoal` / `SlimeRandomDirectionGoal` 就是这么干的）：

- 新增 `SlimeMoveControlAccessor`（`@Mixin(targets = "…Slime$SlimeMoveControl")` +
  `@Invoker setDirection / setWantedMovement`）——内部类是包私有的，只能用 `targets` 字符串定位；
- `TamedSlimeEntity#hopToward(x, y, z, speedMultiplier, aggressive)`：算朝目标的 yaw → `setDirection`
  → `setWantedMovement`，跟随/近战/吞入三个 goal 都改用它，并且**每 tick 调一次**
  （跳一下就停，不能 10 tick 才驱动一次）；
- 跟随时超过 `12 + 4 × blockSize` 格才直接传送（原来写死 12 格，小史莱姆腿短却要拉同样远）；
- 吞入 / 近战 / 跳跃三个 goal 都加了 `getControllingPassenger() != null → 不抢移动`，
  否则主人在体内操控时 AI 会跟玩家的输入打架。

> 顺带修了 `:common:verifyMixins` 自己：`@Mixin(targets = "a.b.C$Inner")` 的值是**点号类名字符串**，
> 而校验器把它当 ASM `Type` 去 `Type.getType(...)`，直接抛 `Invalid descriptor` 把整个任务搞崩。
> 现在字符串形态会走 `name.replace('.', '/')`。

**（2）体内按 WASD 完全无效：26.x 的"客户端权威"模型。**
26.x 把玩家操控的实体默认当成**客户端权威**：

```java
Entity#isLocalInstanceAuthoritative():
    客户端 → isLocalClientAuthoritative()   // 控制器是不是本地玩家
    服务端 → !isClientAuthoritative()        // 客户端权威就不模拟
Player#isClientAuthoritative() → true        // 所有玩家都是 true
```

于是在服务端 `isLocalInstanceAuthoritative() == false` → **服务端不模拟**这头被骑的史莱姆；
而客户端的 `getControllingPassenger()` 依赖 `ownerUuid`，那份数据**从来没有同步到客户端**
（只在 NBT 里），客户端也认不出"这是我在骑" → 两边都不动 → WASD 全灭。

修法：史莱姆显式改成服务端权威（`isClientAuthoritative() → false`），
服务端用 `ServerPlayer#getLastClientInput()` 驱动跳跃移动（`getRiddenInput` / `travel` 里已有这套逻辑），
客户端照常接收位置同步。

**（3）模式切换按钮"点了没反应"。** 指令其实改了（服务端 `setCommand` + 动作栏提示都生效），
但按钮文字写死成 `justarod.slime.command.follow`，永远不刷新，看起来就像没反应。
现在 `SlimeMenu` 多了第 5 个同步槽 `syncCommand`，`SlimeScreen` 每 tick 用它刷新按钮文字（`模式：跟随 / 待命 / 吞人`）。

**（4）透明度。** 直接量了原版 `slime.png`：外壳像素 alpha = **180/255（≈70% 不透明）**，
内核/眼睛是 255。所以在体内看不出去、在外面看不清里面。
现在 `JRTamedSlimeRenderer#getModelTint` 给整体乘一个 alpha（`ARGB.color(115, …)`）：
外壳 ≈ 0.71 × 0.45 ≈ **0.32**，真正像一层胶质。副作用是内核/脸也一起变透
（模型是整体提交的）——想让脸保持不透明，需要把外壳拆成独立图层（原版 `SlimeOuterLayer` 那种做法）。

**（5）诊断日志全部清掉。**
`PacketDebugMixin` / `MenuInitDebugMixin` 已删除并从配置里注销，
`SlimeMenu.dumpDebug`、`SlimeScreen` 的 2 秒转储、`sendInitialSync` 的日志、
`initializeContents`/`setItem`/`setRemoteSlot` 的计数器也一并删掉。
只留下真正有用的那一个：`ServerPlayerSyncAccessor`（容器同步器要用，不是日志）。


### 9.15 实体页排版、分解掉落、跳跃式操控（第六轮）

**（1）实体页为什么糊成一团。** 三件事叠在一起：

1. 面板底是 `0xC0101010` **半透明**的 → 底下的箱子槽位网格直接透出来；
2. 槽位本身还在被原版渲染（物品图标、悬停高亮）→ 和文字互相压；
3. 容量行画在 `topPos+112`、底栏按钮在 `topPos+126`，而 `extractLabels` 又调了 `super`
   把原版的「物品栏」标签画在同一片区域 → 三行字糊在一起（截图里那一团）。

修法：

- 实体页的容器槽位在菜单里统一 `isActive() == false`（`tab != TAB_ENTITIES`）——
  原版对 inactive 槽位**不渲染**，于是没有网格、没有图标、也点不动；
  `mayPlace` / `mayPickup` 一并跟着 `isActive()`，避免盲操作把物品塞进看不见的格子；
- 面板改成**不透明**（`0xFF1B1B1B` + 上下描边），尺寸与 6 行槽位区完全对齐（162×106）；
- 版式全部提成常量（`PANEL_X/Y/W/H`、`PANEL_HEADER`、`ROW_H`、`COL_*`），
  行内四列：图标 / 名字+占格 / 挣扎进度条+百分比 / 取出按钮；名字按像素截断，
  隔行深浅 + 悬停高亮；一屏 4 行，放不下时底部提示「还有 N 个未显示」；
- 悬停与点击共用 `isOverRelease(...)`，不再两处各写一套坐标（之前渲染和点击的判定框是对不上的）；
- `extractLabels` **不再调 super**：只画标题，干掉「物品栏」那行；容量改到实体页面板表头。

**（2）分解实体要掉落物。** 旧代码是 `discard()`——东西直接蒸发，什么也不掉。
现在走 `settleDecomposedEntity(...)`：`stopRiding()` 之后用
`LivingEntity#hurtServer(level, source, Float.MAX_VALUE)` 让它「正常死亡」，
掉落物与经验照常（这也是 `LivingEntity#kill(ServerLevel)` 内部的做法）。
伤害来源优先用 `damageSources().playerAttack(主人)`——不少掉落表只在
「玩家击杀」时才生效，用 `genericKill()` 会缺东西；主人不在线才退回 `genericKill()`。
打不死的实体（无敌等）兜底 `discard()`，避免留下孤儿乘客。

> 顺带记一笔：`LivingEntity#dropAllDeathLoot` 是 `protected`，
> 在**别的**实体实例上调用是编译不过的（Java protected 的跨实例规则），所以只能走 hurtServer。

**（3）「吞人模式」改名「吞噬模式」**（en: Devour mode），同步改了注释里的叫法。

**（4）被操控时也必须是跳的。** 旧实现是 `moveRelative(...) + move(...)` 每 tick 平移，滑得很怪。
现在 `travelRiddenHopping(...)` 照抄 `Slime.SlimeMoveControl` 的节奏：

- 有方向键输入 → 按输入方向（以主人视线为基准，W 前 / A 左…）设朝向；
  按 A 它会**自己转身**再跳，而不是横着滑；
- 落地后 `rideHopCooldown` 数到 0 才 `getJumpControl().jump()`（间隔 5 tick），
  空中 `setSpeed(0.32)` + `super.travel(new Vec3(0, 0, 1))` 保持前进 → 一蹦一蹦；
- 空格 = 立刻再跳一次（把间隔清零）；
- 松手就 `setSpeed(0)`，交给父类的重力/摩擦自然落地停下。


### 9.16 体内内容渲染、权限、粘液球回血（第七轮）

**（1）为什么体内内容「渲染不出来」——是渲染阶段问题，不是位置问题。**
外壳和内核都是半透明，而且都在**实体主渲染阶段**提交；体内的乘客同样在这个阶段被提交，
于是画面上永远是「先画内容、再用壳(0.32) + 核(0.45) 两层半透明色盖上去」：

```
最终可见度 ≈ (1 - 0.32) × (1 - 0.45) ≈ 18%
```

也就是说乘客其实一直在画，只是被压成了 18% 的幽灵，肉眼只剩一层壳（看起来就像只渲染了壳/披风）。
物品更彻底：客户端 `storage().items()` 永远是空的（那份数据不在实体同步范围内），图层自然画不出东西。

修法（一次性把两件事都解决）：

- **内容统一在图层阶段画**：`SlimeContentsLayer` 现在同时画「体内乘客的缩小版」和「体内物品图标」。
  图层是在模型提交**之后**执行的，所以画出来的是真正可见的东西，不会被壳/核盖住；
- 原版那次乘客渲染重新用 `SlimePassengerRenderMixin` 关掉（否则会出现一大一小两个分身）；
- 缩放的算法：外壳在模型空间里是 0.5 格、渲染器又乘了 `blockSize * 2`，
  所以「实体高度占外壳的 60%」对应 `scale = 0.6 / (2 × 实体高度)`；
- 位置沿用空腔中心 `(0, 1.25, 0)`，黄金角螺旋散布，半径收紧到 0.09 格（内核只有 0.375 格见方）。

**（2）体内物品的同步：只发 id。**
新增 `SlimeContentsPayload`（服务端 → 客户端）：实体 id + 最多 25 个**物品注册 id**（varint）。
不发完整 `ItemStack` 是有意的——体内最多 724 格，组件（潜影盒之类）能把包撑爆，
而渲染只要一个图标；实测两个物品的包 **5 字节**。

- 触发：`SlimeStorage` 加了 `version` 计数器，所有会改物品的入口（`addItem` / `consumeOneItem` /
  `removeItem` / `drainItems` / `pollFirstItem` / `ensureSlots`，以及 GUI 侧的
  `SlimeStorageContainer#setChanged` / `removeItemNoUpdate` / `clearContent`）都会 `bumpVersion()`；
- 服务端每 5 tick 比一次版本号，变了就推给 48 格内的玩家（含体内的主人）；
- 客户端缓存 `SlimeClientContents`（按实体 id），图层直接取用。

**（3）权限：非主人不能开背包、不能投喂。**
以前空手右键别人（非主人）的史莱姆会**直接打开背包**，潜行右键和喂物品也没有校验。
现在：

- `mobInteract`：潜行开背包、手拿可堆叠物品投喂、空手交互全部要求 `isOwner`（否则提示「这不是你的史莱姆」）；
- `openContainer` 自己再兜一层（别处调用也拦得住）；
- `SlimeMenu#stillValid` 加 `slime.isOwner(player)`：即使通过别的途径被塞进菜单，
  服务端下一 tick 也会自动关掉（`ServerPlayer#tick` 会检查 `containerMenu.stillValid`）。

**（4）粘液球自动回血。** 每 100 tick（5 秒）检查一次：血量没满 + 体内有粘液球 →
`consumeOneItem` 吃掉一个并 `heal(1.0)`，冒两颗心粒子。消耗会 `bumpVersion()`，
所以体内的图标也会跟着更新。


### 9.17 体内渲染的真正拦路虎：半透明管线**会写深度**

第七轮把内容挪到图层阶段画，结果第三人称还是看不到体内的人，第一人称反而看到一个**倒着的**玩家。
两个现象各自对应一个硬事实：

**（1）`RenderPipelines.ENTITY_TRANSLUCENT` 用的是 `DepthStencilState.DEFAULT`，
也就是 `writeDepth = true`（`javap` 核对过构造过程；另外它的 `withCull(false)`，
所以内外两面都画）。** 深度测试规则是「谁先提交谁挡住后面的」：

```
主模型（外壳，半透明但写深度）→ 之后的图层内容全部深度测试失败 → 第三人称什么都看不见
第一人称：相机在壳内，内容比壳的任意面都近 → 通过深度测试 → 反而看得见
```

这也解释了另一个一直没注意的老毛病：**脸根本看不到**——外壳在模型里排在 `inner` 前面，
写深度之后 `inner`（内核 + 眼睛 + 嘴）全被深度测试挡掉了。

**（2）图层空间是「+Y 朝下」的模型空间**（`LivingEntityRenderer` 先 `scale(-1,-1,1)` 再进图层），
而实体渲染器假设 +Y 朝上、并且自己内部还会再翻一次 → 直接提交就是**倒过来**的。
物品模型则是 +Y 朝上，需要单独补一个「正规旋转」。

修法（提交顺序 + 两个补正）：

| 顺序 | 内容 | 说明 |
| --- | --- | --- |
| 1 | 主模型 `JRTamedSlimeModel` | **只剩脸**（眼睛 + 嘴巴）。外壳和内核都搬走/删掉 |
| 2 | `SlimeContentsLayer` | 体内乘客（缩小版）+ 物品图标 |
| 3 | `SlimeShellLayer` | 外壳：最后叠加一层颜色，只负责「泡在胶里」的观感 |

- 外壳独立成 `JRTamedSlimeShellModel` + `SlimeShellLayer`，**画在内容之后**，
  于是它不再写深度挡住内容，只是把内容染上一层胶质色
  （外壳 alpha = 贴图 0.71 × 0.5 ≈ 0.36 → 内容约 64% 可见）；
- **删掉内核 cube**：它是 6 像素（0.375 格）的实心方块，比体内内容还大，
  会把内容的整个轮廓罩住 → 同样靠深度挡掉内容。删掉之后脸也终于能透出来了；
- 体内乘客：`poseStack.mulPose(Axis.ZP.rotationDegrees(180))` 抵消实体渲染器内部那次翻转，
  模型才是正的（否则倒立）；缩放算法在第九轮改成了「按模型包围盒」，见 §9.18；
- 体内物品：`poseStack.mulPose(Axis.XP.rotationDegrees(180))`（正交旋转，不会把模型镜像）；
- 第一人称不画**自己**（相机就在自己脑袋里，画出来只是一圈内壁）；第三人称照常画，
  于是「在外面能看见体内的自己」。


### 9.18 体内实体「被异常放大」：缩放基准从碰撞箱换成模型包围盒（第九轮）

**（1）现象与根因。** 美西螈（金)被吞进史莱姆后，画出来比外壳还大，整个身体捅在壳外面。

旧算法按**碰撞箱高度**算缩放：

```java
float scale = (float) (ENTITY_FILL / (2.0 * passenger.getBbHeight()));   // 0.6 / (2 × 0.42) = 0.714
```

这只在「模型高 ≈ 碰撞箱高」时成立。美西螈恰恰是最坏的反例——又长又扁：

| 项 | 数值 |
| --- | --- |
| 碰撞箱（`EntityType`） | 0.75 × **0.42** 宽高 |
| 模型包围盒（`AdultAxolotlModel`，离线量出） | 0.875 宽 × 0.75 高 × **1.688** 长（格） |

也就是说，它拿 0.42 当「身高」去缩，结果水平方向被放大到 **外壳边长的 241%**（截图里那一幕）。
同类问题还有一批实体：它们的碰撞箱**根本不反映渲染尺寸**——

| 实体 | 碰撞箱 | 实际渲染尺寸 | 说明 |
| --- | --- | --- | --- |
| 美西螈 | 0.75×0.42 | 最长 1.69 格 | 扁长模型 |
| `TamedSlimeEntity` | 固定 0.5×0.5 | 最长 `blockSize` 格（T5 = 5.5） | 体积在外壳图层里，主模型只剩脸 |
| `RodEntity` | 0.5×0.5 | 1.1875 × (1+长度基因) 格 | GeckoLib 模型 + 遗传学缩放 |
| 幼年生物 | 减半 | 模型还要再乘渲染器的 0.5 | 渲染器自己缩 |

**（2）修法：量「画出来多大」，按最长边缩，并把中心摆到空腔中心。**

- 新增 `SlimeContentSizing`（客户端）：给出实体的**模型包围盒**，单位就是图层空间的格。
  - `LivingEntityRenderer#getModel()` 是 public 的 → 拿 `Model` → `ModelPart#getExtentsForGui`
    遍历所有立方体顶点（`javap` 核对过：它会应用部件 pivot，单位 16 像素 = 1 格——
    实测原版史莱姆外壳正好量出 0.5 格，与 §9.17 的坐标约定一致）；
  - 实体自身的 `scale` 属性（`state.scale`）与**渲染器自己的缩放**都要先乘进临时
    `PoseStack`：后者写在 `LivingEntityRenderer#scale(...)`（protected，跨包调不到），
    于是加了 `LivingEntityRendererScaleInvoker`（`@Invoker`）——**虚调用**，子类覆写照常生效
    （`JRTamedSlimeRenderer` 的 `blockSize * 2`、岩浆怪按体积、幼年 0.5 倍都会算进去）；
  - 结果与碰撞箱取**较大者**：模型量废了也不会缩得比碰撞箱还小（最差退回旧行为）；
  - 量不到（GeckoLib 的渲染器不是 `LivingEntityRenderer`、空模型）就退回碰撞箱。
- 新增 `org.cneko.justarod.api.VisualSized`：**模型与碰撞箱差得远**的自家实体自己报尺寸
  （`TamedSlimeEntity` 报 `tier().blockSize()`、`RodEntity` 报模型高 × 遗传学长度 × 幼年 0.5）。
  接口只返回一个 float、不依赖客户端类，所以服务端加载这两个实体也没问题。
- `SlimeContentsLayer` 的缩放改成**按最长边**：

  ```java
  // 外壳在模型空间只有 0.5 格（8 像素），目标是最长边 = ENTITY_FILL × 0.5 格
  float scale = (float) (ENTITY_FILL * SHELL / size.maxDimension());
  // 实体是「从脚往上长」的：把中心压到空腔中心（原来脚踩在中心，上半身必然捅出去）
  double centerY = CAVITY_Y + size.bottomOffset() * scale + size.height() * scale * 0.5;
  ```

- 水平/竖直散布半径按内容自身尺寸夹住（`半径 ≤ 半壳 − 半个内容`），
  于是**内容再大也不会顶出壳外**，黄金角螺旋只负责让多个内容不重叠。

**（3）离线验证**（`.tmp/jrtest/AxolotlFitProbe.java`，纯几何、不开 GL）：

```
美西螈(成年) 模型包围盒: 宽 0.875 高 0.750 长 1.688 (格)
原版史莱姆外壳      : 宽 0.500 高 0.500 长 0.500 (格)  ← 单位与坐标约定核对通过

外壳边长 2.85 格（T3）
   旧算法: 体内美西螈 高 3.05 格、水平 6.87 格  →  水平占外壳 241%
   新算法: 体内美西螈 高 0.76 格、水平 1.71 格（占外壳 60%）, 竖直占 0.76..1.52 格（外壳 0..2.85）
```

也就是：旧算法 241%，新算法正好 60%（即 `ENTITY_FILL`），且竖直方向严格落在壳内、居中。
玩家/牛/鸡这类「高度就是最长边」的生物，两条公式算出来完全一样，因此没有回归。

**（4）顺带把 mixin 校验器补全。** `:common:verifyMixins` 原来只校验 `@Inject` 的目标方法，
`@Invoker` / `@Accessor` 写错名字或签名（泛型擦除后必须逐字一致）编译器一声不响、
运行期类加载直接崩。现在它也校验这两类目标，并且**比对描述符**
（负例测试：把 `@Invoker("scale")` 的参数类型改成 `Object` → 任务立刻报出
「声明的是 `(Ljava/lang/Object;…)V`，目标是 `(L…LivingEntityRenderState;…)V`」；
`@Inject` 侧写了完整描述符的注入点同样比对，负例 `shouldRender(DDDD)Z` → 报出
「声明的是 `(DDDD)Z`，目标是 `(DDD)Z`」）。
`suspect` 细节：同名重载与编译器生成的**桥接方法**必须逐个试，只要有一个对上就算过
（`AvatarRenderer#extractRenderState` 就同时有
`(Avatar, AvatarRenderState, F)` 与桥接 `(Entity, EntityRenderState, F)`，
只看第一个同名方法会误报——第一版校验器就踩了这个坑）。
本次新增的 `LivingEntityRendererScaleInvoker` 与 `SlimePassengerCullMixin` 都靠它验：
`校验了 42 个 @Inject 目标、6 个 @Invoker/@Accessor 目标 → ✅ 全部目标方法存在`。

**（5）补上第二道闸：被吞实体在**公共段**就不再提交渲染。**
第九轮修完之后症状没消失——玩家看到的「被放大的实体」根本**不是这一层画的**，而是
原版乘客渲染画的那一份：实体是真实乘客，原版会按 `getPassengerAttachmentPoint`
把它摆进体内，但**按原尺寸**画一遍（美西螈截图里脚踩地、身体捅出壳外、颜色没被壳染过，
全是这一份的特征；两份同时在，就会看到「一大一小两个分身」）。

`SlimePassengerRenderMixin` 本来就在 `EntityRenderDispatcher#shouldRender` 拦了一次，
但它挂在 mixin 配置的 `"client"` 段：**只要构建产物里的 `justarod.mixins.json`
是旧的**（只重编了代码、没重跑 `processResources`），这道闸就静默失效，症状原样复现。
所以现在在**公共段**（`mixins`，与驯服/信任那些一定生效的 mixin 同段）再加一道
`SlimePassengerCullMixin`：拦 `Entity#shouldRender(DDD)Z`——也就是
`EntityRenderer#shouldRender` 的第一步判断，返回 false 后实体根本不会被提取。

- 公共段是否安全：`Entity.shouldRender` 是公共代码，全仓扫描只有客户端
  `EntityRenderer` 与 `ForkRocketEntity` / `ThrownTrident` 两个子类引用它，服务端不调用；
  本类也不引用任何客户端类，专用服务器加载没问题；
- 两道闸的分工：client 段那道省掉了「提取渲染状态」的开销，公共段这道保证**即使
  client 段没生效也拦得住**；
- 顺带说明：`SlimeContentsLayer`（图层里那份缩小版）才是唯一该被看见的；两道闸都生效时，
  体内实体只画一次。


### 9.19 体内实体「原尺寸」，不再撑满外壳（第十轮）

**（1）上一轮还错在哪：`ENTITY_FILL` 会把小实体放大。**
第九轮把缩放改成「按最长渲染边缩到外壳边长的 60%」——对**装不下**的实体是对的，
但对**装得下**的实体就成了**额外放大**：

| 外壳 | 美西螈（本身 1.69 格长）在体内被画成 |
| --- | --- |
| T3（2.85 格） | 1.71 格（≈ 原尺寸，看着正常） |
| T5（5.5 格） | **3.30 格（放大到 1.95 倍）** |

同理，鸡、Rod、小史莱姆丢进大史莱姆里都会「越养越大」，这显然不是想要的效果
（玩家原话：*为什么一定要额外放大实体呢？*）。

**（2）新规则：默认原尺寸，装不下才缩。**

```java
// ① 原尺寸：图层 → 世界的倍率是 2 × blockSize（渲染器的缩放），乘 1/(2*blockSize) 正好抵消
double naturalScale = 1.0D / (2.0D * blockSize);
// ② 装不下才缩：多个内容均分外壳，每个最多占 ENTITY_FIT(=0.9)
double fitScale = ENTITY_FIT / (2.0D * contentCount * size.maxDimension());
float scale = (float) Math.min(naturalScale, fitScale);
```

- 实体始终由**它自己的渲染器**按正常姿势/动画/光照画出来，位置在空腔中心（`CAVITY_Y`），
  尺寸就是它在世界里本来的大小；
- 只有「比外壳还大」（或一次吞了多个、平分后放不下）时才等比缩小到装得下；
- 上方那个 `min` 里的 `naturalScale` 就是「不许放大」的硬保证——**任何情况下体内实体都不会
  比它平时更大**。

**（3）离线验证**（`.tmp/jrtest/AxolotlFitProbe.java`，量真实 `AdultAxolotlModel`）：

```
外壳边长 2.85 格（T3）
   旧算法:               高 3.05 格、水平 6.87 格（占外壳 241%）
   第十轮(原尺寸):        高 0.75 格、水平 1.69 格  ← 与它的本体一模一样，竖直 1.06..1.81 居中
外壳边长 5.50 格（T5）
   第十轮(原尺寸):        高 0.75 格、水平 1.69 格  ← 不再被放大（第九轮会画成 3.30 格）
外壳边长 1.00 格（装不下，T0 假设）
   第十轮(缩到装得下):    高 0.40 格、水平 0.90 格，竖直 0.30..0.70 居中
```

**（4）为什么仍然由图层画、而不是直接放回原版渲染。**
两者在**外观上已经完全一致**（同样的渲染器、同样的原尺寸、同样被外壳染上胶质色），
差别只在提交阶段：

- 图层阶段画：内容在「史莱姆自己那一次提交」里，紧跟外壳之前 → **必定看得见**
  （深度上不会被外壳挡住）；
- 原版乘客渲染：它是**另一次实体提交**，和史莱姆按相机距离排序；乘客挂点在体内，
  距离和史莱姆几乎相同 → 谁先谁后不稳定，一旦史莱姆先画，外壳写下的深度会把体内内容
  整块挡掉——这正是 §9.16「体内内容看不见」的老毛病。

所以现在把「原版那一份」用两道闸拦掉（§9.18），只留图层这一份，尺寸是原尺寸：
外观与原版渲染一致，但可见性是确定的。


### 9.20 玩家在体内第三人称「看不见自己」：外壳改成自定义几何提交（第十一轮）

**（1）现象。** 实体渲染已经正常了，但**玩家**钻进史莱姆、开第三人称时看不见自己——
除非把镜头转进壳里。也就是说：普通生物看得见，只有玩家被挡。

**（2）根因：26.x 的提交是分批次的，而玩家的模型落在另一个批次。**

```
renderSolidFeatures():       Shadow → ModelFeatureRenderer(实体模型) → ModelPart → Flame → Leash
                             → Item → Block → CustomFeatureRenderer → Particle
renderTranslucentFeatures(): Shadow → ModelFeatureRenderer(半透明模型) → ModelPart → NameTag → Text
                             → Item → Block → CustomFeatureRenderer
```

- **普通生物**的模型用 `entityCutout` → 进 `renderSolidFeatures` → 永远排在外壳前面 →
  外壳只是盖在它上面（所以第九/十轮之后「实体正常」）；
- **玩家**的模型是 `entityTranslucent`（皮肤要支持半透明像素，`AvatarRenderer` 就是这么选的）
  → 和外壳挤在同一个 `renderTranslucent` 批次里，而那个批次**按到相机的距离排序**
  （`TranslucentModelSubmit.position` → `-lengthSquared()`，远的先画）：
  外壳的提交点在史莱姆脚下、玩家的提交点在体内偏上，第三人称俯视时外壳更远 → **外壳先画**，
  它写下的深度就把体内的自己整块挡掉了；镜头一转进壳里，外壳的近面跑到相机后面，人才露出来。
  这解释了为什么「只有玩家、只有第三人称、只有镜头在外面」看不见。

**（3）修法：外壳不走 `submitModel`，改走 `submitCustomGeometry`。**
自定义几何落在 `CustomFeatureRenderer`——它是**半透明批次里最后一个**功能渲染器：

```java
collector.submitCustomGeometry(poseStack,
        RenderTypes.entityTranslucent(JRTamedSlimeRenderer.TEXTURE),
        (pose, consumer) -> {                 // 回调延迟执行：pose 是提交时拷贝的快照
            PoseStack local = new PoseStack();
            local.last().set(pose);
            this.shellModel.root().render(local, consumer, lightCoords, overlayCoords, SHELL_TINT);
        });
```

于是外壳**必定后画**：内容（含玩家模型）先画、外壳只负责罩色，
既不可能挡住内容，又保留「泡在胶质里」的观感。用的还是同一个渲染类型
（同样的光照、同样的深度写、同样的 alpha），只是**批次顺序**变了。

> 顺带核对（`javap` 结论）：`CustomFeatureRenderer$Storage.add` 会
> `poseStack.last().copy()`，并按 `RenderType.hasBlending()` 分流到 `translucentCustomGeometrySubmits`；
> `renderTranslucentFeatures()` 对**同一个** `SubmitNodeCollection` 依次调用
> Shadow → Model → … → Custom，所以「同一个史莱姆体内」的内容一定先于外壳绘制
> —— 这是引擎结构决定的，不依赖我们提交的先后。

**（4）脸的渲染类型顺手改成 cutout。** `JRTamedSlimeModel` 原来也是 `entityTranslucent`：
它会在半透明批次里、脸的位置写下一片**看不见的深度**（贴图该处像素 alpha = 0，但深度照样写），
把体内内容抠出几个 2×2 像素的小洞。改成 `entityCutout` 后：透明像素直接丢弃（不再写深度）、
不透明像素效果完全一样，而且整张脸进了「实心」批次、永远排在外壳之前。

## 10. 第十二轮：体内开背包 · 主人可被分解 · 手动「吞噬」技能

本轮三件事（作者确认过的需求）：

| # | 需求 | 实现要点 |
| --- | --- | --- |
| A | 玩家**在史莱姆体内**时能打开史莱姆背包 | 新按键 `B` + 新动作包，服务端校验「载具是自己的史莱姆」 |
| B | 分解实体**不再看是不是主人**，主人也可以被分解 | `isAllyOf` 不再把主人算作友军 |
| C | 手动「吞噬」技能：骑着史莱姆按键吞掉前方生物 | 新按键 `G`，4 倍放大动画 + 自定义黏糊吞咽声 + 右侧提示 |

### 10.1 体内开背包：为什么必须另开一个按键

钻进体内后玩家是**乘客**，右键交互全部走「操控载具」那条路，
`Player#interactOn` 不会调到 `TamedSlimeEntity#mobInteract`——
也就是说「潜行右键开背包」那套在体内**根本触发不了**（§9.5 的同类问题）。
所以只能按键 + 包：

```
客户端 tick: B 键 → ACTION_OPEN_BAG
服务端 handle: player.getVehicle() instanceof TamedSlimeEntity v && v.isOwner(player)
              → JRSlimeNetworking.open(player, v)
```

服务端那道 `isOwner` 校验是硬性的（否则任何乘客都能开别人的背包），
客户端那句只是省一次无用发包。

`ACTION_OPEN_BAG` 与 `ACTION_DEVOUR` 都放在「必须已经开着我们的菜单」那道检查**之前**：
玩家在体内时通常并没有界面——按背包键的那一刻正是要把它打开。

### 10.2 主人可被分解：`isAllyOf` 去掉「主人」这一条

`isAllyOf` 原本把自己、主人、同一主人的其它驯服史莱姆都算友军，
而 `findSwallowTarget` 会跳过友军 → **主人永远进不了自己史莱姆的体内**，
也就永远谈不上被分解。现在只保留「自己 + 同一主人的其它驯服史莱姆」。

三个调用点的行为变化，逐个核对过：

| 调用点 | 变化 |
| --- | --- |
| `findSwallowTarget`（自动吞入） | 不再因「是主人」而跳过——但下一行的 `if (candidate instanceof Player) continue` 依旧拦住玩家，**所以不会出现「路过的主人被自动吞掉」** |
| `devourTargetsInCone`（手动技能） | 不拦玩家 → 主人可以被自己的史莱姆吞掉、进而被分解（需求要的正是这个） |
| `OwnerTargetGoal` | 该 goal 用的是 `owner.getLastHurtMob()`，那个目标不可能等于主人自己，**行为无变化**（主人打自己史莱姆时它不会反过来打主人） |

结算沿用现有的 `settleDecomposedEntity`：按**正常死亡**处理，
掉落物与经验照常，伤害来源挂主人（玩家死亡则进入重生流程）——
这是需求明确选的「和别的实体一致」。

### 10.3 手动「吞噬」技能

**数量规则**：`上限 = min{剩余空间, 史莱姆等级}`，同时每个目标仍按**碰撞箱体积**占格。

这两个是不同量纲的上限，必须同时满足，所以 `devourBatch()` 是「逐个试吞 + 扣减剩余空间」，
而不是简单取前 N 个——否则会算错成「一次吞 3 只、每只单独看都装得下、合起来装不下」。
实测体积（`DevourRuleTest`）：玩家 16 格、鸡 2 格。

| 等级 | 内部空间 | 数量上限 | 空仓能吞几只鸡（2 格/只） | 空仓能吞几个玩家（16 格/个） |
| --- | --- | --- | --- | --- |
| T0–T2 | 1 / 3 / 8 | 0 / 1 / 2 | **0**（被 `canSwallowEntities` 拦住） | **0** |
| T3 | 27 | 3 | 3（占 6 格） | 1（体积上限压过等级上限） |
| T4 | 64 | 4 | 4（占 8 格） | 4（占 64 格，正好） |
| T5 | 166 | 5 | 5 | 5（占 80 格，等级才是瓶颈） |

> 等级 0~2「严格吞不到东西」是由两道门共同保证的：
> `canSwallowEntities()`（等级 ≥ 3，与现有收纳门槛一致）先拦一次，
> `devourCapacity()` 对 T0 再返回 0。`devourCapacity` 本身**只**管数量上限，
> 所以它对 T1/T2 会算出 1/2 —— 这是刻意的，别把它当成门槛。

**判定范围**：史莱姆碰撞箱外扩 **3 格**，且只认**骑手视线前方 ±60°（共 120°）锥体内**的目标。
朝向取**骑手的视线**而不是史莱姆自己的 yaw——被操控的史莱姆只在收到移动输入时才转向，
站着不动时它朝哪边是上一次行走留下的；玩家按 G 的直觉是「我准星指着的那一片」。

**只不吞一个人**：正在操控这头史莱姆的主人（他就是骑手，吞进去等于把自己挤下来）。
其余一切活体都吞，**包括玩家**（需求确认「什么都吞」），被吞的玩家会收到
「你被 X 吞进了体内」的提示，之后照常挣扎/漂移逃出。

**节奏**（需求确认）：先把史莱姆放大到 4 倍 → 吞噬 → 再变回原来的大小。

```
t=0        按 G：校验（冷却/等级/目标/空间）→ 全部通过才暂存目标 + 开始动画
t=0..9     放大：1.0 → 4.0，ease-out（先快后慢，像被撑开）
t=9        峰值：执行吞噬 + 播放黏糊吞咽声 + 粒子 + 提示
t=9..18    收缩：4.0 → 1.0，smoothstep（收口）
t=600      冷却结束（30 秒，**每头史莱姆各自记账**，随存档保存）
```

校验不通过时**不进冷却**（避免「按错一下白等 30 秒」），并给出区分开的提示：
附近没目标 / 前方有目标但装不下 / 它还太小吞不下。

### 10.4 放大动画为什么能两端一致（且不用每 tick 发包）

动画进度用 **`level.getGameTime()`** 做时间基准，而不是实体自己的 `tickCount`：
gameTime 在客户端与服务端是**同一个值**（tickCount 是实体年龄，客户端实体中途加载时会偏）。
于是客户端渲染器只要拿「自己的 gameTime − 同步过来的起始时刻」就能还原进度，
还能顺带用 `partialTick` 插值——同步实体数据照常在每 tick 末同步，动画自然跟手。

同步的是三个字段（`SynchedEntityData`）：

| 字段 | 作用 |
| --- | --- |
| `DATA_DEVOUR_ANIM_START`（long） | 动画起始 gameTime |
| `DATA_DEVOUR_ANIM_ACTIVE`（boolean） | 是否正在放动画 |
| `DATA_DEVOUR_ANIM_TICKS`（int） | 动画总时长（分母） |

> 「是否在放动画」单独用一个布尔量，而不是「起始时刻 == 某个哨兵值」：
> gameTime 是任意大的正数，任何整型哨兵理论上都可能撞上真实时间，
> 把「没在放动画」误判成「在放动画」。第一版就是拿 `Integer.MIN_VALUE` 当哨兵，
> 后来换成 gameTime 才发现这个隐患。

**纯视觉效果**（需求确认）：碰撞箱、内部空间、容量、骑乘挂点、粒子位置全都不动，
只在渲染器里多乘一个倍数：

```java
float size = blockSize * 2.0F * Math.max(1.0F, state.devourScale);
```

⚠️ 但 `SlimeContentsLayer`（体内内容）原本用 `1/(2*blockSize)` **抵消**渲染器缩放来还原「原尺寸」，
渲染器多乘一个倍数之后，那里也必须跟着**除**掉，否则会看到「壳张开了、体内的东西还是原来那么大」，
像壳在漏气。外壳图层不用管——它复用同一个 poseStack，自动跟着放大。

### 10.5 音效：自己合成的黏糊吞咽声

需求明确「不要吃东西的声音，要黏糊糊的吞入音」。原版没有合适的音色
（`ENTITY_GENERIC_EAT` 是咀嚼，`SLIME_*` 是弹性挤压），所以**合成**一个：

- 脚本：`.tmp/slime_sound/gen_swallow.py`（numpy 逐样本合成 → ffmpeg 编 Vorbis）
- 资源：`assets/justarod/sounds/slime_swallow.ogg`（11.7 KiB、mono 44.1 kHz、0.95 s）
- 注册：`assets/justarod/sounds.json` 的 `slime_swallow` + `JRSounds.SLIME_SWALLOW`

音色不是「一层噪声糊到底」，而是拆成有先后、频谱各不相同的四个动作：

| 时间 | 动作 | 合成方式 |
| --- | --- | --- |
| 0.06–0.30 s | 吸吮 | 中低频带通噪声（180→1900 Hz，带宽先张开后收拢）——湿摩擦感 |
| 0.24–0.40 s | 第一口「咕」 | 210→120 Hz 的下滑正弦 + 颤音 |
| 0.32–0.62 s | 黏泡 | 7~11 个随机短爆点，每个是「高频共振铃声 + 极快衰减的噪声」——才有「啵」的听感 |
| 0.40–0.95 s | 吞下 | 150→42 Hz 的更长下滑 + 58 Hz 软闷响收尾 |

整体再做 55 Hz 高通 + 4.2 kHz 低通（湿声是**闷**的，高频只在泡破时出现）。
实测频谱质心 ≈ 1675 Hz、主频 ≈ 115 Hz、分段 RMS 呈「-31 → -15 → -35 dB」的起伏
（确认是「一下一下的动作」而不是平铺噪声）。

> 另外两个音色变体（更低沉 / 更短促）留在 `.tmp/slime_sound/alt/`，
> 直接覆盖 `slime_swallow.ogg` 即可换，不用改代码。

### 10.6 屏幕右侧提示

`JRSlimeHud` 挂在 `VanillaHudElements.SUBTITLES` **之后**：

```java
HudElementRegistry.attachElementAfter(VanillaHudElements.SUBTITLES, id, element);
```

选这个锚点而不是 `addLast`：这个位置属于「游戏内 HUD」层，
打开暂停菜单 / 选项 / F3 调试屏时原版**整层不画**，提示自动跟着消失；
`addLast` 画在最外层，会在调试屏和菜单上留一行浮字。

面板三行：`史莱姆 Lv.N` / `按 G 吞噬`（或 `冷却 Ns` / 附近没有可吞噬的生物）/ `按 B 打开背包`，
按键名走 `KeyMapping#getTranslatedKeyMessage()`，所以玩家改键后提示跟着变。

**提示该不该亮**要同时满足两个来源：

- 服务端（权威）：`SlimeDevourStatePayload` 推来的 `cooldownTicks` 与 `targetCount`
  （过滤规则全在服务端算，客户端不复制一份，否则两边迟早不一致）；
- 客户端（粗判）：本地实体列表再核一遍「前方 3 格锥体内还有没有活物」——
  服务端每 5 tick 才推一次，生物完全可能在这几十毫秒里走开或被吞掉。

粗判**故意宽松**（不查空间/友军/等级）：宁可让提示亮着、按下去被服务端拒绝，
也不要出现「明明能吞却显示灰的」。

### 10.7 踩坑：客户端没有 `ownerUuid`，别拿它做按键门禁（这次 B/G「按了没反应」的真凶）

第十二轮第一版把两个新按键写成了「客户端先自查 `isOwner` 再发包」：

```java
if (vehicle is TamedSlimeEntity && vehicle.isOwner(player)) { 发送 ACTION_OPEN_BAG }
```

结果 **B 和 G 完全没反应**——注意是「连提示都没有」，说明包根本没发出去、服务端压根没被调用。

根因：**归属的真相是 `ownerUuid`，而它从不参与实体同步**。
它只存在于服务端字段与存档 NBT 里（`addAdditionalSaveData` / `readAdditionalSaveData`），
客户端的 `ownerUuid` 恒为 `null` → `isOwner()` 恒为 `false` → 那两个 `if` 永远不成立。

> 这是**同一个坑第二次**咬人：§9.14 的「主人在体内按 WASD 没反应」，
> 根因也是客户端的 `getControllingPassenger()` 依赖了为空的 `ownerUuid`。

**修法（两层）**：

1. **权限判定一律只放服务端**，客户端按键处理里**不做** `isOwner` 自查——
   `JRSlimeNetworking` 收包后用服务端的 `ownerUuid` 校验，那才是权限边界。
   客户端多一道检查没有任何安全收益，只会制造「按键静默失效」这类难查的问题；
2. 确实需要「是不是我的」这个信息的**展示类**逻辑（右侧提示只该在你自己的史莱姆上出现），
   就把**主人名字**同步给客户端（`DATA_OWNER_NAME`，String 序列化器），
   `isOwner()` 在没有 `ownerUuid` 时退化成比对档案名。

**为什么同步名字而不是同步「是不是你」**：实体同步数据是所有追踪者**共享的一份**，
服务端写进去的「是不是你」对每个客户端含义都不同，根本无法这么用；
必须发一个大家都一样、由客户端自己拿去比对的值。名字只用于 UI，
认错人也只是少显示一行提示，不涉及权限。

> 通用规则：**任何只在服务端赋值的字段，都不要在客户端读来做判断。**
> 26.x 的 `EntityDataSerializers` 没有 UUID 序列化器，所以 `ownerUuid` 这类字段
> 要么同步一个替代值（名字 / 布尔 / 序号），要么干脆不在客户端判断。

### 10.8 第十三~十六轮修正：体内看不到主人 · 骑上去自己往前平移 · 范围定为 6 格 · 分解主人与复活

#### （1）主人明明在体内，实体页却显示「体内没有实体」

`swallowOwner()` 走的是「直接 `startRiding`」，**没有把主人登记进 `storage`**，
而实体页的数据源就是 `storage.containedEntities()` —— 于是列表恒为空。
（技能吞进来的生物走的是 `trySwallow`，那条路登记过，所以只有主人看不见。）

修法用**状态对账**而不是「在每个入口补一次登记」：挂载关系可能被任意路径改变
（钻进来、被技能吞、被别的模组拉下车、死亡、换维度），
与其指望每个入口都记得同步账本，不如每 tick 比一次：

```java
reconcileContainedOwner()   // 服务端 tick，在 enforceContainedEntities 之后
    riding && !registered  → 登记（体积 = 玩家碰撞箱 16 格）
   !riding &&  registered  → 注销，把空间还回去
```

配套两件事：

- **主人免疫挣扎**：主人进来是为了操控史莱姆，如果照常累积挣扎进度，
  他会在约 36 秒后被自动漂移甩出去（玩家 0.35/tick、T3 阈值 250）——
  直接违背「主人进出」的设计。所以 `SlimeStorage` 多了一列 `struggleImmune`
  （随存档保存），`enforceContainedEntities` / `applyStruggle` 都跳过免疫者；
- **界面与权限**：实体页对免疫者显示「主人（在操控）」而不是一条永远不动的空进度条，
  **且不画「取出」按钮**；服务端 `ACTION_RELEASE_ENTITY` 也会拒绝放出主人
  （否则「放出」会变成把自己踢下车的按钮）。要出去仍然是潜行键。

> 副作用（有意为之）：主人现在**占格**了。所以史莱姆装满时主人钻不进去，
> 会收到「体内空间不够了」——这是空间账本一致性的必然结果，比「主人凭空不占地方」更好解释。

#### （2）骑上去之后史莱姆一直往前平移

两层原因，都堵掉了：

1. **`zza` / `speed` 是原版「乘客即司机」模型的公共状态。**
   `Mob#travel` 会自己取 `getRiddenInput(...)` 再 `travelRidden(...)` 把载具往前推，
   所以一个**非主人**的乘客（比如被吞进来的玩家）会让父类实现拿残留的 `zza` 推动史莱姆；
   而 AI 目标（跳跃/跟随）也会写这两个值。现在 `travel()` 里明确：
   **身上有乘客但没人操控时，先 `riddenMovementReset()`（清 zza/speed/跳跃间隔/MoveControl 目标点）再交给父类**，
   并且服务端每 tick 在 AI 之前再清一次（`enforceIdleWhenUncontrolled`）；
2. **`SlimeKeepJumpingGoal` 只有 `canUse` 挡了「有人在操控」，没有 `canContinueToUse`。**
   于是玩家骑上去的那一刻这个 goal 不会停，它 `tick()` 里的
   `setSpeed(...) / setZza(1.0F)` 继续把史莱姆往前推。现在补了 `canContinueToUse` 与 `stop()`
   （`stop()` 里把两个值清零——原版 `Goal#stop` 不会替你清）。
   另加 `addPassenger` 覆写：上车瞬间清一次，专治「骑上去就开始滑」。

> 这三个清零点（上车 / 无操控的每 tick / travel 的兜底）看着重复，但缺一个就会漏：
> zza 是公共可变状态，任何一处写脏都会表现成「它在自己走」。

#### （3）吞噬范围：先改动态，再定为固定 6 格

先是写死 3 格（小史莱姆手短、大史莱姆要贴脸），一度改成按体积动态
`1.0 + 0.5 × 边长`（外扩 2.4~3.75 格），体感仍然太短，最终**定为固定 6 格**。

注意「总触及半径」还要加上外壳半径，所以实际够得着的距离是 `6 + 边长/2`：

| level | 边长(格) | 总触及半径(格) |
| --- | --- | --- |
| 3 | 2.85 | 7.43 |
| 4 | 4.00 | 8.00 |
| 5 | 5.50 | 8.75 |

外扩距离仍然走 `devourRange()` 这一个出口，不再散落常量；
客户端的提示灰化判断直接调它，两边不会漂移。
想恢复动态就把方法体改成 `BASE + PER_BLOCK * tier().blockSize()`（常量注释里留了说明）。

#### （4）两轮才修对：分解主人（第十四 / 十五轮）

这一段有两个**方向相反**的错误，值得完整记下来。

**第一轮：主人登记进 `storage` 后，分解把「正在操控的主人」当猎物。**
`firstContainedEntity()` 是「取登记表第 0 个」，而登记顺序里主人常常排在最前（他先上车）
→ 一喂催化物就把他当第一份内容。接着：

1. `settleDecomposedEntity` 用 `damageSources().playerAttack(owner)` 结算，
   而伤害来源的实体**就是受害者本人**；`ServerPlayer#hurtServer` 先查 `isInvulnerableTo`，
   再用 `canHarmPlayer(来源玩家)` 过滤玩家来源——**自己打自己恒为 false，这一击打不掉血**
   （`javap` 核对过字节码）；
2. 于是落进兜底的 `if (entity.isAlive()) entity.discard()`，
   而对活着的 `ServerPlayer` 调 `discard()` 会把玩家实体整个拆掉
   → 表现就是「史莱姆把主人（连带自己）一起搞没了」。

**第二轮：我「修」错了方向——加了「跳过操控者」。**
当时以为主人是操控者所以不该被分解，于是 `firstDecomposableEntity()` 跳过
`getControllingPassenger()`。但

> `getControllingPassenger()` 的逻辑是「乘客里有主人就返回他」，
> 而主人进到体内的**唯一方式**就是当乘客。

也就是说「跳过操控者」≡「永久跳过主人」——需求「主人也可以被分解」被彻底堵死，
这就是「还是无法分解主人」的原因。

**最终修法：让分解玩家真的能杀死玩家，而不是躲开他。**

- **选择阶段不豁免任何人**：`pickFirstDecomposable(contained, skipId, lookup)`
  就是「按登记顺序取第一个查得到的实体」，`skipId` 只是预留的豁免口子（当前传 null）；
- **结算阶段改用能生效的伤害来源**：受害者与伤害来源是同一人时用 `genericKill()`——
  它不是玩家来源，不经过 `canHarmPlayer` 过滤，玩家会走**正常的死亡 / 掉落 / 重生**流程。
  这正是需求选的「按正常死亡结算，和别的实体一致」；
- **活着的玩家绝不走 `discard()`**：兜底分支只把它 `stopRiding()` 放出来，
  剩下的交给原版（创造模式本来就该死不了）；
- **明确警告**：分解队列轮到主人自己时，先给他一句红色提示
  （`justarod.slime.decompose.self_warning`）——他会真的死，不该是无声无息地暴毙；
- **界面**：实体页对主人显示「主人（可被分解）」，并且**照常画 × 按钮**
  （免疫挣扎 ≠ 不能被分解，也不等于不能被放出来）。

> 教训两条：
> ① **「登记成内容」和「可以被分解」是两件事**，分解的目标集合要单独定义；
> ② **修 bug 前先确认自己修的是哪个方向**——第一轮的问题是「不该动他」，
>    第二轮我修成了「不去动他」，方向正好相反，把一个「会炸」修成了「永远不生效」。
>    这次把挑选逻辑抽成纯函数并写了正/反两向断言（`DevourRuleTest` 第 8 组），
>    再改错方向就会直接红。

#### （5）第三轮：分解致死后复活「还在体内」

上一轮让分解**真的能杀死玩家**之后，新症状出现了：死在体内、点复活，人**还在史莱姆体内**。

根因是原版行为 + 我自己的代码各一半：

1. **原版 `die()` 不会把乘客放下来。** `javap` 核对 `LivingEntity#die` 与
   `ServerPlayer#die` 的字节码：里面**没有** `stopRiding` / `ejectPassengers` 调用。
   也就是说「死了但仍挂在载具上」是原版行为，断开挂载得我们自己来；
2. **而我的 `stopRiding()` 恰好只在「没死」的分支里。** 上一轮的写法是
   `if (entity.isAlive()) { entity.stopRiding(); ... }` —— 玩家**真的死了**的时候
   这个分支不执行，于是挂载关系原样留着；
3. **更糟的是每 tick 的重新挂载。** `enforceContainedEntities()` 里有
   「不是乘客就 `startRiding`」的维护逻辑；死亡到复活之间那个乘客还在
   `getPassengers()` 里，于是它会被反复按回车上，复活后自然还在体内。

**修法三处**：

| 位置 | 改动 |
| --- | --- |
| `settleDecomposedEntity` | **先 `stopRiding()` 再致死**（不是只在存活分支里），客户端在死亡画面前就收到「已下车」 |
| `enforceContainedEntities` | 新增 `isDeadPassenger()`（`isRemoved()` 或 `isDeadOrDying()`）→ 断开挂载、**归还空间**，不再重新按上车；死亡到复活之间也不再占格 |
| `reconcileContainedOwner` | `riding` 判定加上 `!isDeadPassenger(owner)`，死了的主人不再算「在体内」，账本立刻清干净 |

> 另外：上一版加的「分解到自己时的红色警告」按需求**已移除**
> （`justarod.slime.decompose.self_warning` 的 lang 条目也一并删掉）。

> 教训：**「实体死了」不等于「它不再是乘客」。** 涉及载具的逻辑要显式处理死亡，
> 不能指望原版替你下车；而每 tick 维护挂载关系的代码，必须把「死者」排除在外，
> 否则它会把一个已经该被清掉的乘客一直按回车上。

#### （6）潜行键 = 主人钻出（只对主人有效）

`justarod.slime.enter` 的提示里一直写着「潜行键钻出」，但**代码里根本没有这条路径**：
站在外面时的 `mobInteract` 里有一个 `isShiftKeyDown` 分支（那是开背包的），
而钻进体内之后玩家是乘客、右键交互整条路都不会走到 `mobInteract`——
于是「潜行钻出」只是个空头承诺（这也是我上一轮结尾提到「没找到实现」的那件事）。

现在补在 `tickOwnerSneakEscape()`（服务端每 tick）：

```java
if (!(getControllingPassenger() instanceof ServerPlayer owner)) { escapeLatched = false; return; }
boolean sneaking = owner.getLastClientInput().shift();   // 与操控用的 forward/backward 同一份输入
if (!sneaking) { escapeLatched = false; return; }
if (escapeLatched) return;
escapeLatched = true;
releaseEntity(owner.getUUID());       // 注销账本 + 归还空间 + 放到脚下
```

几个刻意的选择：

| 决定 | 原因 |
| --- | --- |
| **只对主人有效** | 被**技能**吞进来的其他玩家要靠挣扎（R）或自动漂移逃出；潜行键对他们无效，否则「被吞」形同虚设 |
| 用 `getLastClientInput().shift()` | 潜行状态在服务端只能这么读（`isShiftKeyDown()` 读的是实体标志，被吞时视线/朝向被锁，不适用） |
| 用 `releaseEntity` 而不是裸 `stopRiding` | 它会一并注销账本、归还空间，并把主人放到**史莱姆脚下**（裸 `stopRiding` 会让他停在体内那个乘客挂点上） |
| 加 `escapeLatched` 松手闩 | 只看「是否按下」的话，**按住潜行键**钻进来的玩家会被立刻弹出去、甚至来回抖动；要求「先松手过一次」才允许下一次逃出 |

> 于是潜行键在两个状态下含义不同：**站在外面**是「开背包」的修饰键（潜行+右键），
> **在体内**是「钻出」。两者不会冲突，因为它们发生在不同的实体状态里。

### 10.9 本轮验收信号

1. 钻进体内按 **B** → 背包打开（别人钻进你的史莱姆按 B 无反应）；
2. 把主人喂进去后启动分解 → 主人被正常分解（掉落 + 经验 + 重生），
   而**主人站在史莱姆旁边时不会被自动吞**；
3. 骑着 T3+ 史莱姆对着鸡群按 **G** → 先放大到 4 倍、听到黏糊吞咽声、吞下 min{空间,等级} 只、再缩回；
4. 冷却 30 秒内右侧显示「冷却 Ns」，冷却结束后没有目标时变灰；
5. `./gradlew :common:verifyMixins` 全绿（本轮没有新增 mixin，42 + 6 个目标不变）；
6. **体内实体页**（§10.8）：钻进体内按 B，实体页应当看到**你自己**占 16 格、
   右侧写「主人（在操控）」且**没有 × 按钮**；技能吞进来的生物照常有 × 与进度条；
7. **别让它自己走**（§10.8）：骑上去立刻松手，史莱姆应当**原地不动**；
   它身上放一个非主人乘客时同样不该平移；
8. **吞噬范围**（§10.8）：T5 的触及半径应明显大于 T3（3.85 → 6.50 格），不必贴着目标才能吞；
9. **分解主人真的生效，而且不会把史莱姆搞没**（§10.8 第 4 条）：
   体内只有你时喂催化物 → 分解完成后你**正常死亡**（掉落物 + 经验 + 重生界面），
   史莱姆**活着留在原地**（不是连它一起消失）。创造模式下应当死不了、只是被放出来；
10. **复活后不再卡在体内**（§10.8 第 5 条）：在体内被分解致死 → 点复活 →
    应当出现在重生点、**身上没有史莱姆**；此时史莱姆的实体页里也不该再有你、空间已归还；
11. **潜行键钻出**（§10.8 第 6 条）：体内按潜行键 → 立刻落到史莱姆脚下并提示「你从史莱姆体内钻了出来」；
    按住不放不会反复进出；被**技能**吞进来的其他玩家按潜行键**没有反应**（只能挣扎/漂移）。
